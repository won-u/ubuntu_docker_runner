# 배경: 내 작업 품질을 끌어올리는 Personal Rules MCP 서버

> 목적: 코드·문서·다이어그램·형상관리 등 **내 모든 프로젝트 산출물의 품질을 일관되게 끌어올린다.**

## 1. 한 줄 요약
내 개인 규칙(코딩 스타일, 커밋 방식, 리뷰 기준 등)을 **위키·노트에 박제해두지 않고, AI가 작업하는 순간 알아서 꺼내 쓰게 만드는 것**입니다. 규칙은 한 곳에만 두고, 어느 프로젝트에서·어떤 AI 도구(Cline/Roo/Claude)를 쓰든 **같은 기준이 자동으로 적용됩니다.**

**무엇을 얻는가**
- **작업 효율:** 몰랐거나 깜빡한 규칙도 AI가 챙겨 줍니다 → **리뷰에서 덜 지적받고, 재작업이 줄어듭니다.** 새 프로젝트에 가도 "여기서는 이렇게 한다"를 도구가 바로 알려 주므로 노트를 뒤질 필요가 없습니다.
- **일관성:** 품질 기준을 매번 떠올려 강제하지 않아도 **알아서 균일하게 맞춰집니다.** 리뷰 시간을 스타일 지적이 아니라 **설계·로직**에 쓰게 되며, 내 노하우가 흩어지지 않고 **한 곳에 규칙으로 남습니다.**

## 2. 왜 지금 필요한가
- 규칙은 있지만 **작업 중에 아무도 위키를 보지 않습니다.** 그래서 표준이 "존재하기만 하는" 상태로 남습니다.
- 품질은 코드만이 아닙니다. 문서, 다이어그램, 커밋/형상관리, 리뷰까지 전방위인데, 기준이 각자 머릿속에만 있어 **리뷰 때마다 같은 지적이 반복됩니다.**
- 이제 작업 상당수가 **AI를 거칩니다.** AI가 우리 기준을 모르면 **도구가 강력해질수록 제각각인 결과물이 더 빠르고 더 많이 생산됩니다.** 표준을 AI에 주입하지 않으면 품질 편차가 오히려 가속됩니다.

## 3. 핵심: 중구난방은 없애되, 개성은 살린다
"규칙이 없으면 각자 스타일이 제각각인 것이 싫다" — 바로 그 지점을 노립니다. 다만 목표는 **모두가 똑같은 결과물을 찍어내는 것이 아닙니다.** 그것은 불가능하고, 사실 바람직하지도 않습니다.

핵심은 **없애야 할 다름과 살려야 할 다름을 구분하는 것**입니다.

- **없애야 할 다름 (노이즈):** 커밋 메시지 형식, 네이밍, 폴더 구조, 에러 처리 위치, 문서 목차, 브랜치 이름 등. 이는 문제가 달라서가 아니라 **사람의 습관이 달라서** 생기는 차이입니다. 정보 가치가 없고 읽는 사람·리뷰어만 피곤하게 만듭니다.
- **살려야 할 다름 (실력·창의):** 어떤 알고리즘을 택했는가, 설계를 어떻게 나눴는가, 트레이드오프를 어떻게 판단했는가. 여기서는 개성이 드러나야 합니다.

이 서버가 AI에 주는 것은 **"답"이 아니라 "틀(규칙)"** 입니다. 그래서 AI는 같은 틀을 **서로 다른 문제에** 적용합니다. 결과물은 **동일하지는 않지만(문제가 다르므로), 형태는 균일해집니다.** 이것이 우리가 원하는 상태입니다.

> 신문에 비유하면 이해가 쉽습니다. 한 신문의 기사들은 **내용은 모두 다르지만**(사건이 다르므로) **레이아웃·서체·문체 규칙은 동일해서** "같은 신문"으로 읽힙니다. 내가 바라는 것도 이와 같습니다 — **여러 프로젝트에 걸쳐 작성했어도 한 결로** 읽히는 코드베이스.

**이 "균일함"이 좋은 이유는 다음과 같습니다.**
- **예측 가능해서 인지 부담이 줄어듭니다.** 형식이 일정하면 남의 코드·문서·커밋을 볼 때 "이 사람의 스타일 해석"에 힘을 쓰지 않고 곧바로 **내용**에 집중합니다.
- **품질의 하한선이 올라갑니다.** 규칙은 "이미 합의한 좋은 방식"을 담고 있어, 신입이 작성하든 급하게 작성하든 **최소한 그 선은 넘깁니다.** 상한(창의)은 막지 않고 **바닥만 끌어올립니다.**
- **리뷰가 본질에 집중됩니다.** 형식 지적은 AI가 미리 처리하므로, 사람은 **로직·설계** 같은 핵심을 봅니다.
- **내 안목이 축적됩니다.** 프로젝트마다 관례를 새로 만드는 대신 내 베스트 프랙티스가 **한 번 정리되어 계속 재사용됩니다.** 시간이 지나도 그 지식은 남습니다.

한마디로, **"똑같이 만들자"가 아니라 "제멋대로인 부분은 없애고, 잘하는 지점에서만 다르게 하자"** 입니다.

## 4. 동작 방식 (비기술 설명)
AI가 상황에 맞춰 **필요한 규칙을 자동으로 가져다 씁니다.**
- 코드 작성 전 → 코딩 표준 참조
- 커밋/PR 전 → 커밋 규약 참조
- 완료 판정 전 → 완료 기준(Definition of Done) 참조
- 비밀·입력·의존성 처리 시 → 보안 가이드 참조
- 리뷰 시 → 코드 리뷰 기준 참조

개발자 입장에서는 **평소처럼 AI에 지시하면 결과물이 이미 우리 기준에 맞춰 나옵니다.** 규칙은 서버 한 곳에만 있으므로, 수정하면 **모두에게 동시에 반영됩니다.** 각자 별도로 설정할 필요도 없습니다(무마찰).

## 5. 구체 예시: 같은 요청, 다른 결과
**예 1 — "방금 작업 커밋해 줘"**
- *서버 없이:* 커밋 메시지가 세션·프로젝트마다 제각각입니다("수정", "fix bug", "wip"…). 형식도 언어도 뒤죽박죽입니다.
- *서버 있음:* AI가 커밋 규약을 참조해 `<type>(module): 요약` 형식, 제목 영어·본문 한글, 맥락→구현→영향 구조로 **일관되게** 작성합니다.

**예 2 — "이 데이터 파싱 함수 하나 짜 줘"**
- *서버 없이:* 네이밍·에러 처리 위치·입력 검증 여부가 그때그때 다릅니다.
- *서버 있음:* AI가 코딩 표준과 보안 가이드를 참조해 내 네이밍 규칙, 경계 입력 검증, 정해 둔 에러 처리 방식을 **기본으로** 반영합니다.

두 경우 모두 **결과물(커밋 내용, 함수 로직)은 각자 다르지만, 형식과 기준은 균일**합니다 — 섹션 3에서 말한 그 상태입니다.

## 6. 제공 범위 — 코드만이 아니라 전방위
"규칙을 AI에 실시간으로 제공한다"는 틀은 코드에 국한되지 않고 산출물 전체로 확장됩니다.

| 품질 영역 | 예시 규칙 | 상태 |
|---|---|---|
| 코드 | 언어별 코딩 표준(C++/TS/Python/Bash/공통) | ✅ 제공 중 |
| 워크플로우 | Plan→confirm→실행, 정직한 테스트·보고 | ✅ 제공 중 |
| 형상관리 | 커밋 규약, atomic commit, PR 작성 | ✅ 제공 중 |
| 완료 기준 | Definition of Done(포맷·린트·타입·테스트·빌드) | ✅ 제공 중 |
| 보안 | 시크릿 처리, 입력 검증, 의존성 정책 | ✅ 제공 중 |
| 코드 리뷰 | 리뷰 기준·PR 체크리스트 | ✅ 제공 중 |
| **문서** | 문서 작성 표준, README/주석/ADR 규약 | ✅ 제공 중 |
| **다이어그램** | 표기 규약(C4/시퀀스 등), 네이밍·범례 규칙 | ✅ 제공 중 |
| **브랜치/릴리즈** | 브랜치 네이밍, 릴리즈·태깅 전략 | ✅ 제공 중 |
| **테스트·API·의존성·로깅** | 테스트 표준, API 설계, 의존성 관리, 로깅/관측성 | ✅ 제공 중 |

→ 새 영역 추가는 대부분 **마크다운 파일 하나를 얹는 것으로 끝납니다.** 틀은 이미 동작하고 있습니다.

> **현재 구현 상태 (이미 동작 중):** Streamable HTTP MCP 서버(Express, 단일 `/mcp` 엔드포인트)에 도구 22개와 프롬프트 2개가 등록되어 있고, 선택적 토큰 인증·Docker 배포·호스트 마운트(무재빌드 갱신)·한/영 README·레포 템플릿(CLAUDE.md/AGENTS.md)·배포/보안 결정 문서까지 갖춰져 있습니다. 즉 **개념검증(PoC)이 아니라 지금 시연 가능한 상태**입니다.

## 7. 기대 효과 (Before → After)
| 항목 | Before | After |
|---|---|---|
| 표준 실효성 | 위키엔 있으나 실제 작업엔 미반영 | 작업하는 순간 자동 적용 |
| 품질 편차 | 프로젝트·세션마다 제각각(중구난방) | 형태는 균일, 알맹이는 각자 |
| 리뷰 | 같은 형식 지적 반복 → 왕복 증가 | 형식은 통과, 리뷰는 본질로 |
| 새 프로젝트 착수 | 관례를 매번 다시 떠올림 | 도구가 표준을 즉시 안내 |
| 유지보수 | 표준이 여러 곳에 흩어짐 | 한 곳만 수정하면 전 프로젝트 반영 |
| 확장 | 프로젝트마다 복붙 | 공통은 중앙, 프로젝트별은 각 레포 |

**점검도 가능합니다.** 리뷰 재작업 비율, 표준 위반 지적 건수, 새 프로젝트 착수 시간, 커밋/문서 규약 준수율을 도입 전후로 비교합니다.

## 8. 위키·복붙으로는 왜 부족한가
- **위키만 두는 경우:** 작업 중에 열어보지 않고, 최신 상태가 유지되지 않으며, "작업 시점"에 개입하지 못합니다.
- **레포마다 파일을 복붙하는 경우:** 프로젝트마다 복사되어 곧 서로 어긋납니다(drift).
- **그래서 하이브리드 모델:** **개인 공통 규칙은 중앙 서버(단일 소스)**, **프로젝트별 빌드/테스트 등은 각 레포.** 두 영역이 겹치지 않아 중복·불일치가 없습니다.

## 9. 한계와 전제 (정직하게)
- **유도이지 강제가 아닙니다.** 서버는 AI에 규칙을 "제공"할 뿐 100% 준수를 보장하지 않습니다. 최종 강제선은 여전히 CI·린트·리뷰입니다. 이 서버는 그 **앞단에서 애초에 기준에 맞게 나오도록 유도**해 위반 자체를 줄입니다 — **CI의 대체가 아니라 보완**입니다.
- **결과는 규칙의 품질에 좌우됩니다.** 제공하는 규칙이 부실하면 결과도 부실합니다. 그래서 baseline 문서를 **우리 실제 정책으로 채우는 초기 작업**이 필요합니다.
- **클라이언트 지원 편차가 있습니다.** 도구/프롬프트/instructions 인식은 클라이언트·버전마다 다를 수 있어, 핵심 유도는 CLAUDE.md 등 **여러 경로로 이중화**합니다.
- **외부 노출 시 추가 조치가 필요합니다.** 현재는 내부용 전제이며, 외부 공개 시 TLS 등은 별도 문서로 관리합니다(`docs/reverse-proxy-tls.md`).

## 10. 예상 반론과 답
- **"어차피 안 지킬 것이다."** → 사람의 의지에 맡기지 않습니다. **AI가 작업 시점에 자동 적용**하므로 개발자에게 요구되는 행동 변화가 거의 없습니다.
- **"관리 부담이 크지 않은가."** → 규칙은 마크다운 파일입니다. 외부에서 갱신하면 **서버 재빌드 없이 즉시 반영됩니다.**
- **"보안은 괜찮은가."** → 내부용이며 읽기 전용입니다. 접근은 토큰으로 통제하고, 외부 노출 시 TLS/프록시 방안은 별도 문서로 관리합니다.
- **"특정 도구에 종속되지 않는가."** → **표준 MCP 프로토콜**을 따르므로 Cline/Roo/Claude가 공통으로 연결됩니다. 규칙은 순수 마크다운이라 언제든 이식 가능합니다.

## 11. 도입은 얼마나 드는가
- **내가 할 일:** 각 프로젝트에서 MCP 서버를 **한 번 등록**하는 것이 전부입니다. 이후에는 평소대로 AI를 쓰면 됩니다.
- **운영:** 작은 Node 서버 1개(Docker)면 됩니다. 규칙은 마크다운이라 갱신은 파일 수정으로 끝나며 **재빌드가 필요 없습니다.**
- 인프라·학습 부담이 낮아 **시작 문턱이 매우 낮습니다.**

## 12. 로드맵
- **Phase 1 (완료):** 코드 중심 공통 규칙 — 코딩 표준·워크플로우·커밋·DoD·보안·리뷰. 서버·인증·문서 구축.
- **Phase 2 (완료):** 문서/다이어그램/브랜치·릴리즈, 테스트·API 설계·의존성·로깅 규약으로 영역 확장(도구 22개).
- **Phase 3:** 실제 프로젝트에 적용 → 사용감 점검 → 레포 템플릿(CLAUDE.md/AGENTS.md)으로 프로젝트 전반에 확산.

## 13. 다음 단계
1. **먼저 적용할** 프로젝트 1개를 고릅니다.
2. 각 영역의 baseline 문서를 내 실제 정책으로 채웁니다.
3. 해당 프로젝트에서 **클라이언트 등록**(1회 설정)을 마칩니다.
4. 얼마간 써 본 뒤 **효과를 점검**하고 나머지 프로젝트로 확산을 결정합니다.

---

> **요약:** 표준을 문서로 재워두지 말고 AI가 작업하는 순간 자동으로 사용하게 만듭니다. 그러면 **제멋대로인 부분은 사라지고 잘하는 지점에서만 달라지는** — 동일하지는 않아도 균일한 결과물이 나옵니다. 이것이 내 모든 프로젝트의 품질을 기억력에 의존하지 않고 끌어올립니다.
