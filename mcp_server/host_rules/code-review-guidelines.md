# Code Review Guidelines (개인 코드 리뷰 기준)

> 업계에서 일반적으로 통용되는 코드 리뷰 기준이다. 개인 특화 규칙은 이 문서에 추가한다.
> **원칙: 결함을 막고, 유지보수 가능하며, 일관된 코드를 남긴다.** 리뷰는 흠집 잡기가
> 아니라 코드 품질과 지식 공유를 위한 협업이다.

## 리뷰어가 보는 것 (우선순위 순)

### 1. 정확성 (Correctness) — 최우선
- 로직이 의도대로 동작하는가. 요구사항을 실제로 충족하는가.
- **edge case·경계값**을 다루는가: 빈 값·null·0·음수·매우 큰 값·off-by-one.
- 에러 경로가 올바른가. 실패 시 어떻게 되는가.
- 동시성/경쟁 조건(race), 순서 의존, 재진입 문제는 없는가.

### 2. 보안 (Security)
- 비밀 하드코딩, 입력 미검증, 인젝션, 잘못된 인가(IDOR) — `security-guidelines.md` 기준 위반이 없는가.
- 신뢰 경계에서 외부 입력을 검증하는가.

### 3. 테스트 (Tests)
- 변경/신규 로직에 대한 테스트가 있는가.
- 테스트가 **의도된 동작**을 단언하는가(구현에 억지로 맞춘 tautological 테스트가 아닌가 — `workflow-rules.md` §2).
- 주요 비즈니스 로직·edge case가 케이스에 포함됐는가. CI가 green인가.

### 4. 에러 처리 & 자원 관리
- 실패를 **조용히 삼키지** 않는가(`catch {}` 빈 블록 등). 복구 불가면 컨텍스트를 담아 전파/로깅하는가.
- 파일·커넥션·락 등 자원을 확실히 해제하는가(`finally`/`with`/RAII).
- 외부 I/O에 타임아웃·재시도가 적절한가.

### 5. 가독성 & 유지보수성
- 이름이 의도를 드러내는가. 함수가 한 가지 일만 하는가. 깊은 중첩 대신 early-return을 쓰는가.
- 주석이 **"왜"**를 설명하는가("무엇"은 코드가 이미 말함).
- 죽은 코드·주석 처리된 코드·매직 넘버가 없는가.

### 6. 단순성 & 설계 (Simplicity)
- **과설계·조기 추상화**가 없는가. 요청받은 것만 구현했는가.
- 중복이 불필요하게 늘지 않았는가(반복되면 추출). 기존 코드를 재사용했는가.
- 모듈 경계·책임 분리가 합리적인가.

### 7. 성능 (합리적 범위)
- 명백한 비효율(N+1 쿼리, 불필요한 루프·복사·할당)이 없는가.
- 자료구조 선택이 적절한가. **단, 조기 최적화는 지양** — 측정 없는 미세 최적화보다 명확성이 우선.

### 8. API·호환성·일관성
- 공개 인터페이스의 하위 호환성이 깨지지 않는가. 계약(입출력·에러)이 명확한가.
- 프로젝트·언어 코딩 표준과 네이밍 컨벤션을 따르는가.

## 머지를 막는 것 (Blocking)
- 빌드·테스트 실패, CI red.
- 보안 결함(비밀 유출, 미검증 입력, 인젝션, 잘못된 인가), 알려진 심각 취약점.
- 테스트 없는 신규 비즈니스 로직.
- 정확성 결함(잘못된 로직, 처리되지 않은 edge case/에러).
- 커밋 규약 위반(`commit-guidelines.md`), atomic하지 않은 커밋.

## 막지 않는 것 (Non-blocking / nit)
- 취향·스타일 선호는 `nit:` 으로 표시하고 머지를 막지 않는다(포매터·린터로 자동화하는 것이 이상적).
- 범위를 벗어난 개선 제안은 후속 이슈로 남긴다.

## PR 위생 (작성자)
- PR은 **작고 집중되게**. 큰 변경은 논리 단위로 나눈다(리뷰 가능성↑).
- PR 설명에 **무엇을·왜·어떻게 테스트했는지**를 적는다.
- 리뷰 코멘트에 **모두 응답**하고, 반영 시 근거를 남긴다. 리뷰를 개인 감정으로 받지 않는다.

## 리뷰 태도 (리뷰어)
- **코드를 대상으로**, 사람을 대상으로 하지 않는다. 정중하고 구체적으로.
- 지적은 **`파일:라인` + 구체적 개선안(또는 질문)**과 함께. "왜"라는 근거를 제시한다.
- 좋은 부분도 언급한다. 확신이 없으면 단정 대신 질문으로.
- 리뷰는 **빠르게**(가능하면 하루 내) 돌려 흐름을 막지 않는다.

## 승인 기준
- 위 blocking 항목이 없고, 남은 것이 nit뿐이면 승인 가능하다.
- 확신이 서지 않는 복잡·위험 변경은 추가 리뷰어를 요청한다.
