# Data & Persistence (개인 데이터·영속성 기준)

> 데이터베이스·스키마·마이그레이션 등 영속 데이터 취급에 일반적으로 통용되는 기준이다. 개인 특화 규칙(특정 DB·ORM 관례 등)은 이 문서에 추가한다.
> **원칙: 데이터는 코드보다 오래 산다. 스키마 변경은 되돌릴 수 있게, 무결성은 DB가 지키게 한다.**

## 1. 스키마 설계
- 도메인을 반영해 **정규화**를 기본으로 하고, 성능상 필요할 때만 의도적으로 비정규화한다(이유를 남긴다).
- 제약(NOT NULL·UNIQUE·FK·CHECK)을 **DB 레벨**에서 건다 — 애플리케이션 검증만 믿지 않는다.
- 타입을 정확히 쓴다(돈은 정수·decimal, 시간은 timezone-aware, 열거는 명시적).

## 2. 마이그레이션
- 스키마 변경은 **항상 마이그레이션 파일**로 한다 — 수동 DDL 금지. 마이그레이션도 코드처럼 리뷰·커밋한다.
- **무중단·전방 호환**을 기본으로: 컬럼 삭제·이름변경은 (1)추가 → (2)양쪽 쓰기 → (3)백필 → (4)읽기 전환 → (5)제거의 단계로 나눈다.
- 각 마이그레이션은 **되돌릴 수 있어야**(down) 하며, 적용 전 백업을 전제한다.
- 대용량 백필은 배치로 나눠 잠금·부하를 피한다.

## 3. 트랜잭션 · 일관성
- 함께 성공·실패해야 하는 쓰기는 **하나의 트랜잭션**으로 묶는다.
- 트랜잭션은 **짧게** 유지한다(외부 API 호출·긴 작업을 트랜잭션 안에 넣지 않는다).
- 동시성 충돌은 낙관적 락(버전 컬럼)이나 적절한 격리수준으로 다룬다(→ `error-handling-resilience.md` 재시도).

## 4. 쿼리 · 성능
- 파라미터 바인딩만 쓴다 — 문자열 조립 쿼리 **금지**(→ `security-guidelines.md`).
- 조회 패턴에 맞춰 **인덱스**를 건다. N+1 쿼리를 피한다(→ `performance-guidelines.md`).
- 목록은 항상 **페이지네이션**한다(→ `api-design-guidelines.md`).

## 5. 데이터 수명 · 안전
- 백업·복구 절차를 정하고 **복구를 실제로 검증**한다(백업은 복구될 때만 유효하다).
- 개인정보(PII)는 최소 수집·보관하고 보존기간을 정한다(→ `security-guidelines.md`).
- 삭제는 소프트 삭제 여부·법적 보존요건을 고려해 설계한다.
