# Error Handling & Resilience (개인 에러 처리·복원력 기준)

> 오류 처리와 외부 의존 환경에서의 복원력에 일반적으로 통용되는 기준이다. 개인 특화 규칙(특정 프레임워크 예외 체계 등)은 이 문서에 추가한다.
> **원칙: 실패는 정상 경로다. 조용히 삼키지 말고, 예측 가능하게 실패하고, 회복 가능한 것만 회복한다.**

기본 오류 처리 원칙은 `coding-standards/general.md` 와 언어별 문서에 있다. 이 문서는 **복원력 패턴**에 집중한다.

## 1. 실패 다루기
- 실패를 **조용히 삼키지 않는다**(빈 catch 금지). 처리하지 못할 오류는 컨텍스트를 담아 전파한다.
- 예상 가능한 실패(검증 실패·자원 없음)와 버그(불변식 위반)를 구분한다. 전자는 값·결과 타입으로, 후자는 fail-fast 로.
- 오류 메시지에 **무엇이·왜** 실패했는지 담되, 비밀·PII 는 넣지 않는다(→ `security-guidelines.md`).

## 2. 경계에서 방어
- 신뢰 경계(사용자 입력·외부 API·파일·네트워크)에서 **검증하고 실패를 가정**한다. 내부 계약은 신뢰한다.
- 설정·필수 전제는 **시작 시점에 검증**해 즉시 죽는다(fail-fast → `configuration-management.md`).

## 3. 외부 호출 복원력
- 모든 네트워크·IO 호출에 **타임아웃**을 건다(무한 대기 금지).
- 일시적 실패는 **지수 백오프 + 지터**로 재시도하되 **멱등**한 작업에만. 재시도 상한을 둔다.
- 반복 실패하는 의존성은 **서킷 브레이커**로 빠르게 차단해 연쇄 장애를 막는다.
- 과부하 시 **백프레셔**(큐 상한·거절)로 자신을 보호한다.

## 4. 우아한 성능저하 (Graceful Degradation)
- 비핵심 의존성이 죽어도 **핵심 기능은 살린다**(예: 추천 실패 시 빈 목록으로 계속).
- 부분 실패를 호출자·사용자에게 **명확한 상태**로 알린다(전부-아니면-전무를 강요하지 않는다).

## 5. 관측 · 정리
- 삼킨 것이 아니라 **처리한** 오류도 적절한 레벨로 로깅한다(→ `logging-observability.md`).
- 실패 경로에서도 자원(커넥션·파일·락)을 확실히 해제한다(`finally`·`with`·RAII).
- 재시도·타임아웃·차단 이벤트를 메트릭으로 남겨 복원력 동작을 관측 가능하게 한다.
