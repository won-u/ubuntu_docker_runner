# Performance Guidelines (개인 성능·효율 기준)

> 성능·효율에 일반적으로 통용되는 기준이다. 개인 특화 규칙(목표 지연·처리량 SLO 등)은 이 문서에 추가한다.
> **원칙: 추측하지 말고 측정한다. 올바르게 만든 뒤, 병목만 최적화한다.**

## 1. 측정 우선
- **조기 최적화 금지** — 정확·단순하게 먼저 만든다(→ `coding-standards/general.md`).
- 최적화 전에 **프로파일링·측정**으로 진짜 병목을 찾는다. 체감·추측으로 고치지 않는다.
- 최적화 후 **다시 측정**해 개선을 수치로 확인하고, 회귀를 막을 벤치마크를 남긴다.

## 2. 알고리즘 · 자료구조
- 핫패스의 **복잡도**(시간·공간)를 의식한다. 입력이 커질 때의 스케일을 먼저 본다.
- 용도에 맞는 자료구조를 고른다(조회는 맵, 정렬·범위는 트리 등).
- 상수배 미세최적화보다 **알고리즘 개선**이 대개 더 크다.

## 3. IO · 네트워크 · DB
- 흔한 병목은 CPU가 아니라 **IO**다. 왕복 횟수를 줄인다(배치·캐시·프리페치).
- **N+1 쿼리**를 피하고 필요한 컬럼만 가져온다(→ `data-persistence.md`).
- 비동기·병렬로 대기시간을 겹치되, 과도한 동시성은 오히려 해가 됨을 유의한다.

## 4. 캐싱
- 캐시는 강력하지만 위험하다 — 무엇을·얼마나·언제 무효화할지 정하고 도입한다.
- 무효화 전략(TTL·이벤트 기반)을 명시하고, 스테일 데이터의 허용 범위를 정한다.
- 캐시 없이도 **정확**해야 한다. 캐시는 성능 수단이지 정합성 수단이 아니다.

## 5. 메모리 · 자원
- 큰 데이터는 **스트리밍**으로 처리한다(전체를 메모리에 올리지 않는다).
- 자원(커넥션·버퍼·핸들)은 풀링·재사용하고 확실히 해제한다.
- 불필요한 할당·복사를 줄이되, 가독성을 크게 해치면서까지 하지 않는다.
