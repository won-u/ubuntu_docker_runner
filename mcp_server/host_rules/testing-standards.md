# Testing Standards (개인 테스트 기준)

> 업계에서 일반적으로 통용되는 테스트 작성 기준이다. 개인 특화 규칙(도구·커버리지 목표 등)은 이 문서에 추가한다.
> **원칙: 테스트는 "의도된 동작"을 검증하고, 빠르고 결정론적이어야 한다. 초록불(green)이 신뢰를 뜻해야 한다.**

## 1. 왜 테스트하는가
- 회귀를 막고, 리팩터링을 안전하게 하며, 의도를 문서화한다.
- 테스트는 **구현이 아니라 동작(계약)** 을 검증한다. 내부 구현을 바꿔도 동작이 같으면 테스트는 통과해야 한다.

## 2. 테스트 피라미드
- **단위(unit)**: 가장 많이. 함수·클래스 단위, 외부 의존 없이 빠르게.
- **통합(integration)**: 중간. 모듈 간 결합·DB·외부 API 경계를 검증.
- **E2E**: 가장 적게. 핵심 사용자 시나리오만. 느리고 깨지기 쉬우므로 최소화한다.
- 상위 계층으로 갈수록 **느리고 불안정**하므로, 가능한 한 낮은 계층에서 검증한다.

## 3. 구조 (가독성)
- **AAA / Given-When-Then**: 준비(Arrange) → 실행(Act) → 단언(Assert)을 명확히 나눈다.
- **1 테스트 = 1 동작**. 한 테스트에서 여러 동작을 뭉뚱그려 단언하지 않는다.
- 테스트 이름은 **무엇을 검증하는지**를 드러낸다(예: `returns 401 when token is missing`).

## 4. 좋은 테스트의 요건
- **결정론적(deterministic)**: 같은 입력에 항상 같은 결과. 시간·랜덤·순서·네트워크에 의존하지 않는다(주입하거나 고정).
- **독립적(isolated)**: 테스트 간 상태를 공유하지 않는다. 실행 순서·병렬성에 무관해야 한다.
- **빠름(fast)**: 단위 테스트는 밀리초 단위. 느리면 자주 안 돌린다.
- **의도 검증**: 구현에 억지로 맞춘 **tautological 테스트**(구현을 그대로 복사한 단언)를 만들지 않는다(`workflow-rules.md` §2). 테스트가 진짜 버그를 잡을 수 있어야 한다.

## 5. 무엇을 테스트하는가
- **경계값·edge case**: 빈 값·null·0·음수·최대값·off-by-one.
- **에러 경로**: 실패 시 올바르게 동작하는가(예외·복구·정리).
- **회귀 재현**: 버그를 고칠 때 **먼저 그 버그를 재현하는 테스트**를 추가한다(같은 회귀 방지).
- 사소한 getter/setter나 프레임워크 코드가 아니라 **비즈니스 로직**에 집중한다.

## 6. 테스트 더블 (Mock/Stub/Fake/Spy)
- 외부 의존(네트워크·시간·파일·랜덤)은 경계에서 대체한다.
- **과도한 mock 지양**: 구현 세부에 밀착된 mock은 리팩터링을 방해한다. 가능하면 **fake**(간단한 인메모리 구현)를 선호한다.
- 내가 소유하지 않은 타입을 mock 하지 말고, **경계(어댑터)** 를 두고 그것을 대체한다.

## 7. 커버리지
- 커버리지는 **지표이지 목표가 아니다**. 100%를 위해 의미 없는 테스트를 만들지 않는다.
- **중요 경로·분기·에러 처리**가 덮였는지가 라인 커버리지 수치보다 중요하다.
- 커버리지 급감은 리뷰에서 신호로 본다(`code-review-guidelines.md`).

## 8. 플레이키(flaky) 테스트
- 간헐적으로 실패하는 테스트는 **신뢰를 파괴**하므로 즉시 다룬다(격리 또는 수정, 방치 금지).
- 흔한 원인: 시간·타임존, 실행 순서 의존, 동시성/경쟁, 정리되지 않은 전역 상태, 실제 네트워크 호출.
- `sleep`으로 타이밍을 맞추지 말고 **조건 대기(polling/이벤트)** 로 바꾼다.

## 9. CI 연계
- 모든 테스트가 **green** 이어야 병합·완료로 간주한다(`definition-of-done.md`).
- 테스트는 로컬과 CI에서 **동일하게** 실행되어야 한다. 신규 로직에는 테스트를 함께 추가한다.
