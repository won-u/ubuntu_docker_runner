# Workflow Rules (개인 작업 절차 기준)

> 기능·이슈·문서 등 모든 작업에 공통으로 적용되는 절차다. 개인 특화 규칙(도구·환경 등)은 이 문서에 추가한다.
> **원칙: 모든 작업은 계획→사용자 확인→실행, 테스트, 빌드 성공, 정직한 보고를 거친다.**
>
> **우선순위(규칙셋 전체에 적용)**: 이 규칙셋은 **프로젝트 규칙이 없을 때의 기본값**이다.
> 프로젝트 저장소의 규칙(`CLAUDE.md`/`AGENTS.md`, 린터·포매터 설정 등)이 이 규칙셋과
> 충돌하면 **프로젝트 규칙이 우선**한다. 단 **안전(비밀 취급·보안)과 정직한 보고는
> 양보하지 않는다** — 이 둘은 프로젝트 규칙으로도 무를 수 없다.

기능 추가 / 기능 수정 / 이슈 분석 / 이슈 해결 / 문서 업데이트 등 **모든 동작**에
아래 5개 절차를 무조건 적용한다.

## 1. Plan 우선 · 사용자 confirm 후 실행
- 어떤 작업이든 **먼저 Plan 을 작성**한다(목표, 변경 범위, 영향, 테스트 방법, 리스크).
- Plan 을 **사용자에게 제시하고 confirm 을 받은 뒤에만** 실제 작업을 시작한다.
- confirm 전에 임의로 선행 구현하지 않는다. Plan 이 바뀌면 다시 confirm 을 받는다.
- **Plan 과 진행 todo 를 `plan/<slug>.md` 파일에도 기록**하고 작업 진행에 따라
  갱신한다(in-chat todo 와 내용 일치). `plan/` 은 gitignore 되는 로컬 작업 파일로,
  사용자가 채팅 히스토리를 스크롤하지 않고도 계획·todo 진행상황을 파일로 다시
  확인할 수 있게 하기 위함이다. 파일은 한 태스크(여러 phase 포함)당 하나로 두고,
  각 단계는 체크박스(`- [ ]` / `- [x]` / 진행중 `- [~]`)로 표기한다.

## 2. 테스트 필수 · 정직한 판정
- 기능 추가 시 **unit test 를 반드시 작성**하고 통과시킨다. 주요 비즈니스
  로직·edge case·예외 상황을 케이스에 포함한다. **외부 경계(DB·API·파일·
  네트워크)를 넘거나 컴포넌트 간 상호작용이 있으면 integration test 도 함께
  작성**한다(테스트 피라미드 → `testing-standards.md`).
- **테스트를 동작에 억지로 맞춰 통과시키지 않는다.** 테스트는 *의도된 동작*을
  기준으로 단언(assert)하며, 구현이 틀렸으면 **실패하도록** 둔다. 실패를 숨기거나
  기댓값을 구현에 맞게 바꿔 통과시키는 행위는 금지한다.
- 테스트가 실패하면 원인을 분석해 구현을 고치고, 그래도 의도가 바뀐 경우에만
  사용자 confirm 후 기댓값을 갱신한다.

## 3. 빌드/동작 성공
- 모든 동작은 **빌드와 동작이 성공한 상태**로 마무리한다. 깨진 채로 커밋/종료하지
  않는다.
- 프로젝트의 표준 빌드/실행 방법으로 검증하며, 가능하면 **호스트를 오염시키지 않는
  격리 환경**(예: 컨테이너/전용 빌드 이미지)을 사용한다.
- atomic commit 단위로 독립적으로 빌드가 성공해야 한다(`commit-guidelines.md`).
- **라이브 빌드/작업 트리를 진단·검증 목적으로 직접 `git apply`/`checkout`/`reset`
  하지 말 것** — 손상이 그대로 빌드로 간다. 검증은 temp git(`git show HEAD:<file>`)
  이나 `git worktree` 로 격리한다.

## 4. 작업 보고 · 완료 후 상세 설명 (필수)
- **모든 동작**(기능 추가/수정, 이슈 분석/해결, 문서 업데이트, 설정 변경 등)을
  마친 뒤에는 **사용자에게 무엇을·어떻게·왜 했는지 상세히 설명**한다. 같이 일하는
  사람이 그 설명만 읽고도 진행 내용을 온전히 파악할 수 있어야 한다.
- 보고에는 **다음 4가지를 반드시 포함**한다:
  1. **요청 (What was asked)**: 사용자의 요청/문제가 무엇이었는지 요약.
  2. **원인·판단 (Why)**: (이슈면) 근본 원인, 여러 방안 중 이 방법을 택한 **이유**와
     근거. 추측이 아니라 확인한 사실 기준으로.
  3. **작업 내용 (How / What changed)**: 실제로 바꾼 파일·함수·설정과 핵심 로직을
     구체적으로. 커밋을 남겼다면 커밋 해시/제목도 함께.
  4. **영향·후속 (Impact / Next)**: 이 변경이 미치는 영향, 남은 리스크, 사용자가
     다음에 해야 할 일(재빌드/pull/재현 방법 등).
- **분량은 작업 규모에 비례**한다. 사소한 변경은 짧게, 구조·빌드·이슈 해결처럼
  파급이 큰 작업은 충분히 상세하게. 요점은 "협업자가 맥락 없이도 이해 가능한가"이다.
- 보고를 생략하거나 "완료했습니다"만 남기는 것은 금지한다. **정직하게** 보고하며,
  실패·미완·건너뛴 부분이 있으면 숨기지 말고 그대로 드러낸다.
