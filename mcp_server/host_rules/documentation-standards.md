# Documentation Standards (개인 문서 작성 기준)

> 코드·문서·다이어그램의 문서화에 일반적으로 통용되는 기준이다. 개인 특화 규칙은 여기에 추가한다.
> **원칙: 문서는 코드와 함께 갱신하고, 최신이 아니면 없느니만 못하다.**

## 1. 코드 주석
- 주석은 **"왜"** 를 설명한다("무엇"은 코드가 이미 말한다).
- 공개 API(함수·클래스·모듈)에는 doc 주석(JSDoc/docstring/Doxygen 등)으로 목적·매개변수·반환·예외·부작용을 적는다.
- 죽은 코드·주석 처리된 코드를 남기지 않는다(git이 기억한다). `TODO`/`FIXME` 는 맥락(또는 이슈 키)과 함께.

## 2. README
모든 저장소/주요 모듈의 README에 최소한 다음을 담는다:
- **목적**: 무엇을, 왜 하는가(한두 문단).
- **시작하기**: 요구사항, 설치, 빌드·실행·테스트 명령.
- **사용법**: 대표 예시.
- **구조**: 주요 디렉터리·컴포넌트 요약(또는 링크).
- **설정**: 환경변수·설정 항목.

## 3. ADR (Architecture Decision Records)
- 중요한 기술적 결정(프레임워크 선택, 데이터 모델, 트레이드오프)은 **ADR로 기록**한다.
- 각 ADR은 **맥락 → 결정 → 대안 → 결과**를 간결히 담고, 날짜·상태(제안/수락/폐기)를 표기한다.
- 결정을 바꾸면 새 ADR로 대체(supersede)하고 이전 것을 폐기 표시한다. 저장소 내 `docs/adr/` 등에 번호를 매겨 둔다.

## 4. 작성 원칙
- **형식**: 마크다운. 제목 계층·목록·표로 스캔 가능하게.
- **간결·정확**: 장황함보다 핵심. 예시를 제공한다.
- **독자 기준**: 맥락 없는 협업자가 읽고 이해할 수 있게 쓴다(약어는 처음에 풀어 쓴다).
- **최신성**: 동작·API·설정이 바뀌면 관련 문서를 **같은 변경(PR)에서 갱신**한다.
- **문서도 리뷰 대상**이다. 코드 리뷰와 동일하게 검토한다.
- **규칙 문서 톤**: 이 규칙셋(host_rules) 내에서 정책·가이드라인 문서는 **반말**("~한다"), 언어별 코딩 표준(`coding-standards/`)은 **존댓말**("~합니다")로 통일한다.
