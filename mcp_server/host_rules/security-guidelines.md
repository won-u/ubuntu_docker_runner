# Security Guidelines (개인 시큐어 코딩)

> 언어·프레임워크에 **무관한 원칙**이다. 본문의 구체 예시(특정 함수/API·도구 이름 등)는
> 이해를 돕기 위한 **예시일 뿐 규범이 아니며**, 언어별 구체 방어는 `coding-standards/{language}.md`
> 를 따른다. 반면 알고리즘·프로토콜 표준 이름(bcrypt, AES-GCM, TLS 등)은 언어 무관한 기준이다.
> **핵심: 신뢰 경계에서 검증하고, 안전하지 않으면 실패한다(fail securely).**

## 1. 비밀 정보 (Secrets & Credentials)
- API 키·토큰·비밀번호·인증서를 **코드·로그·주석·커밋·에러 메시지·URL에 하드코딩 금지.** 환경변수나 시크릿 매니저를 사용한다.
- 비밀 파일은 **버전 관리에서 제외**하고, 예시 파일로 키 목록만 공유한다.
- 커밋 전 변경분을 확인해 비밀 유출을 막고, 유출 시 **즉시 회전(rotate)** 한다(삭제만으로 부족 — 히스토리에 남음).
- 비밀은 **URL 경로/쿼리에 넣지 않는다**(로그·리퍼러·프록시에 남음). 헤더나 본문으로 전달한다.

## 2. 입력 검증 & 인젝션 방지 (Input Validation & Injection)
- **모든 외부 입력**(사용자·외부 API·파일·환경변수)을 신뢰 경계에서 **검증·정규화**한다. 화이트리스트(허용 목록) 방식을 우선한다.
- **SQL 인젝션:** 문자열 조립 대신 **파라미터라이즈드 쿼리/프리페어드 스테이트먼트**나 ORM 바인딩을 쓴다.
- **커맨드 인젝션:** 사용자 입력을 셸에 문자열로 넘기지 않는다. 명령을 **인자 배열로 직접 실행**하고 옵션 종료(`--`)를 쓴다.
- **경로 traversal:** 파일 경로에 입력을 쓸 때 상위 경로(`..`)·절대경로·심볼릭 링크를 차단하고, 정규화한 경로가 허용 루트 안인지 검증한다.
- **SSRF:** 사용자가 준 URL로 서버가 요청하기 전에 대상 호스트/스킴을 허용 목록으로 제한한다(내부망·메타데이터 주소 차단).
- **출력 인코딩(XSS 등):** 출력 컨텍스트(HTML/JS/URL/CSS)에 맞게 이스케이프한다. untrusted 데이터를 **DOM·템플릿·쿼리에 그대로 삽입하지 않는다**(예: 브라우저에서 원시 HTML 직접 대입 지양).
- **역직렬화:** 신뢰할 수 없는 입력을 **임의 객체를 자동 복원하는 방식**으로 역직렬화하지 않는다.

## 3. 인증 & 세션 (AuthN & Session)
- 비밀번호는 **전용 비밀번호 해시(bcrypt / scrypt / Argon2(id 권장))** 로 salt와 함께 저장한다. **평문, 그리고 MD5·SHA-1·범용 해시 단독 사용 금지.**
- 세션·재설정 토큰은 **암호학적 난수 생성기(CSPRNG)** 로 생성한다. **범용(비암호학적) 난수를 보안 용도에 쓰지 않는다.**
- 토큰·서명·MAC 비교는 **상수시간 비교**로 한다(타이밍 공격 방지).
- 세션 쿠키에 `HttpOnly`·`Secure`·`SameSite` 를 설정한다. 로그인·권한 변경 시 세션을 재발급한다.
- 가능하면 다단계 인증(MFA)을 지원한다.

## 4. 인가 & 접근 제어 (AuthZ)
- 권한 검사는 **항상 서버 측**에서 한다. 클라이언트가 보낸 역할·ID를 신뢰하지 않는다.
- **모든 요청**에서 리소스 소유권을 확인한다(IDOR 방지 — 남의 식별자로 조회/수정 금지).
- **최소 권한 원칙:** 계정·토큰·서비스에 필요한 최소 권한만 부여한다.

## 5. 암호화 (Cryptography)
- **직접 구현하지 않는다.** 검증된 표준 라이브러리를 쓴다.
- 대칭 암호는 인증된 암호화(AEAD, 예: AES-GCM)를 쓴다. **ECB 모드·고정 IV·하드코딩 키 금지.**
- 전송 구간은 **TLS 1.2+**(가능하면 1.3). **TLS/인증서 검증을 비활성화하지 않는다.**

## 6. 데이터 보호 & 로깅 (Data & Logging)
- PII·민감정보는 **최소 수집**하고, 전송·저장 시 암호화한다. 로그에서 마스킹하고 규제(GDPR 등)·보존 정책을 지킨다.
- 에러 메시지에 **스택 트레이스·내부 경로·쿼리** 등 구현 정보를 사용자에게 노출하지 않는다. 상세는 서버 로그로만.
- 보안 관련 이벤트(로그인 실패·권한 거부 등)는 로깅하되 비밀·PII는 남기지 않는다.

## 7. 의존성 & 공급망 (Dependencies)
- 새 의존성은 **필요성·유지보수 상태·인기도·라이선스**를 확인 후 추가한다.
- **lockfile을 커밋**해 버전을 고정하고, **의존성 취약점 스캐너(SCA)** 에서 알려진 심각 취약점이 없어야 한다.
- 의존성을 주기적으로 업데이트한다. 신뢰할 수 없는 출처의 패키지를 쓰지 않는다(타이포스쿼팅 주의).

## 8. 웹 서비스 (해당 시)
- **HTTPS 전면 적용**, 보안 헤더 설정(예: CSP, HSTS, `X-Content-Type-Options: nosniff`, `X-Frame-Options`).
- 상태 변경 요청에 **CSRF 방어**(토큰/SameSite)를 적용한다.
- **CORS는 최소 허용**(구체 오리진). 와일드카드 `*` + credentials 조합은 금지.
- 인증·비용성 엔드포인트에 **rate limiting** 을 건다.

## 9. 파일 업로드 (해당 시)
- 타입·크기·확장자를 검증하고, 파일명을 정규화(traversal 차단)한다.
- 업로드 파일은 웹 루트 밖에 저장하고, 실행 권한을 주지 않으며, 가능하면 스캔한다.

## 10. 금지·주의 패턴 (Prohibited / High-risk)
- 신뢰할 수 없는 입력의 **동적 코드 실행**(문자열을 코드로 평가하는 방식), 안전하지 않은 역직렬화.
- 검증 없는 리다이렉트(open redirect).
- 보안 용도에 비암호학적 난수 사용.
- TLS/인증서 검증 비활성화, 자체 암호 구현.
- 광범위 권한 토큰, 와일드카드 CORS(+credentials).
