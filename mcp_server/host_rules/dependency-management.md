# Dependency Management (개인 의존성 관리 기준)

> 외부 라이브러리·패키지 관리에 일반적으로 통용되는 기준이다. 개인 특화 규칙(허용 라이선스·사설 레지스트리 등)은 이 문서에 추가한다.
> **원칙: 모든 의존성은 부채다. 신중히 추가하고, 버전을 고정하며, 최신·안전하게 유지한다.**

## 1. 추가 기준 (새 의존성을 들이기 전에)
- **정말 필요한가.** 표준 라이브러리나 이미 있는 의존성으로 해결되면 그것을 쓴다. 사소한 기능을 위해 무거운 의존성을 들이지 않는다.
- **유지보수 상태**: 최근 릴리즈·이슈 대응·활발한 커뮤니티가 있는가. 방치된 프로젝트는 위험하다.
- **크기·전이 의존(transitive)**: 하나를 추가하면 그 하위 의존성까지 딸려온다. 트리 전체의 무게·표면을 본다.
- **라이선스**: 내가/제품이 허용하는 라이선스인가(아래 §5).
- **성숙도·평판**: 널리 검증된 것을 선호한다. 새로 만든/무명 패키지는 신중히.

## 2. 버전 고정 (재현 가능한 빌드)
- **lockfile 을 커밋**해 정확한 버전을 고정한다. 로컬·CI·운영이 **동일한 트리**를 설치해야 한다.
- 설치는 lockfile 기반의 **결정론적 명령**(예: 재현 설치 모드)을 쓴다. lockfile 을 무시하는 설치를 CI에서 쓰지 않는다.
- 버전 범위 정책(정확 고정 vs 캐럿 등)은 프로젝트에서 일관되게 정한다.

## 3. 업데이트
- 의존성을 **정기적으로** 업데이트한다. 미루면 한 번에 큰 위험·breaking change 가 쌓인다.
- 자동화 도구(업데이트 PR 봇 등)로 부담을 줄이되, **changelog·breaking change 를 확인**하고 테스트로 검증한다.
- 보안 패치는 **우선 처리**한다.

## 4. 보안 · 공급망 (Supply Chain)
- **의존성 취약점 스캐너(SCA)** 를 CI에 두고, 알려진 심각 취약점이 없어야 한다(`security-guidelines.md` §7).
- **타이포스쿼팅**(유사 이름 악성 패키지)에 주의한다. 이름·게시자·다운로드 규모를 확인한다.
- 신뢰할 수 없는 출처의 패키지를 쓰지 않는다. 가능하면 **무결성 해시**로 검증한다.
- 필요 시 사설 레지스트리/미러로 공급망을 통제한다.

## 5. 라이선스
- 추가 전 **라이선스 호환성**을 확인한다. 내가 금지한 라이선스(예: 강한 copyleft를 제품 정책상 못 쓰는 경우)를 피한다.
- 라이선스·저작권 고지 의무를 지킨다. 불명확하면 도입 전에 확인한다.

## 6. 최소화 · 정리
- **표면(attack surface)과 무게**를 줄인다. 기능이 겹치는 의존성을 여럿 두지 않는다.
- **미사용 의존성을 제거**한다. 사용하지 않는 패키지는 위험만 남긴다.
- 중복·충돌하는 버전(전이 의존)을 정리한다.
