# Logging & Observability (개인 로깅·관측 기준)

> 서비스·애플리케이션의 로깅과 관측성에 일반적으로 통용되는 기준이다. 개인 특화 규칙(도구·대시보드 등)은 이 문서에 추가한다.
> **원칙: 운영 중인 시스템을 밖에서 이해할 수 있도록, 구조화된 신호를 의도적으로 남긴다. 로그는 디버깅이 아니라 운영을 위한 것이다.**

## 1. 관측성의 세 축
- **로그(Logs)**: 이산적 이벤트 기록("무슨 일이 있었나").
- **메트릭(Metrics)**: 시간에 따른 수치 집계("얼마나·얼마나 자주").
- **트레이스(Traces)**: 요청이 서비스들을 거치는 경로("어디서 느렸나").
- 셋은 상호 보완적이다. 하나로 모든 것을 하려 하지 않는다.

## 2. 로그 레벨 (의미를 지켜 사용)
- **ERROR**: 조치가 필요한 실패. 처리 못 한 예외·불변식 위반. 알림 대상이 될 수 있다.
- **WARN**: 비정상이지만 처리된 상황. 재시도 성공, 폴백 사용, 임박한 한계.
- **INFO**: 정상 운영의 주요 이정표. 기동/종료, 요청 처리 결과, 상태 변화.
- **DEBUG**: 개발·심층 진단용 상세. 운영에서는 기본 비활성.
- 레벨을 남발하지 않는다(모든 것을 ERROR로 찍지 않는다). 레벨은 **운영자의 대응 여부**로 결정한다.

## 3. 구조화 로깅 (Structured Logging)
- 사람이 읽는 문자열 **연결(concat) 대신 key-value(예: JSON)** 로 남긴다. 기계가 파싱·검색·집계할 수 있어야 한다.
- 일관된 필드명을 쓴다(예: `level`, `timestamp`, `service`, `event`, `duration_ms`).
- 자유 서술보다 **구조화된 컨텍스트**를 선호한다: `"user 42 failed"` 보다 `{event:"login_failed", user_id:42}`.

## 4. 무엇을 남기는가
- **요청 경계**: 진입/이탈, 결과 상태, 소요 시간.
- **상태 변화·부수효과**: 생성·수정·삭제, 외부 호출.
- **실패**: 원인·컨텍스트를 담아 로깅한다(스택 트레이스는 내부 로그에만).
- **상관 ID(correlation/trace id)**: 요청 단위로 ID를 부여해 로그·트레이스를 연결한다. 서비스 간 호출에 전파한다.

## 5. 무엇을 남기지 않는가 (중요)
- **비밀·자격증명·토큰·PII** 를 로그에 남기지 않는다. 필요한 경우 **마스킹**한다(`security-guidelines.md` §6).
- 요청 본문·헤더를 통째로 덤프하지 않는다(민감정보 유출·용량 폭증).
- 사용자에게는 구현 세부(스택 트레이스·내부 경로·쿼리)를 노출하지 않는다. 상세는 서버 로그로만.

## 6. 메트릭
- 요청 지향 서비스는 **RED**(Rate·Errors·Duration), 리소스는 **USE**(Utilization·Saturation·Errors)를 기본 관점으로 삼는다.
- **카디널리티 폭발 주의**: user id·요청 id 같은 고유값을 메트릭 라벨로 쓰지 않는다(그건 로그/트레이스의 몫).
- 지표는 **증상(사용자 영향)** 중심으로 설계한다.

## 7. 트레이싱
- 분산 시스템에서는 요청에 **trace/span** 을 부여해 서비스 경계를 넘어 경로를 추적한다.
- 컨텍스트(trace id 등)를 호출 체인에 **전파**한다. 표준(예: W3C Trace Context, OpenTelemetry)을 따른다.

## 8. 알림 (Alerting)
- **증상 기반**(사용자 영향·SLO 위반)으로 알림하고, 원인 나열식 알림은 지양한다.
- 알림은 **행동 가능**해야 한다. 노이즈가 많으면 사람이 무시하게 되므로 정기적으로 정리한다.

## 9. 에러 처리와의 관계
- 실패를 **조용히 삼키지 않는다**(빈 `catch`). 복구 불가면 컨텍스트를 담아 전파하거나 로깅한다(`code-review-guidelines.md`).
- 같은 실패를 여러 계층에서 중복 로깅하지 않는다(한 곳에서 책임지고 남긴다).
