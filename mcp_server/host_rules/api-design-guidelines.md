# API Design Guidelines (개인 API 설계 기준)

> 공개 인터페이스(REST/RPC/라이브러리 API 등) 설계에 일반적으로 통용되는 기준이다. 개인 특화 규칙(프로토콜·표준 스키마 등)은 이 문서에 추가한다.
> **원칙: API 는 계약이다. 명확하고 일관되며, 하위 호환을 지킨다. 한 번 공개하면 소비자가 의존한다.**

## 1. 기본 원칙
- **최소 놀람(least surprise)**: 소비자가 예상하는 대로 동작한다. 관례를 따른다.
- **일관성**: 명명·구조·에러·페이지네이션 규칙을 API 전체에서 동일하게 유지한다. 일관성은 문서보다 강력하다.
- **작게 시작**: 공개 표면을 최소화한다. 나중에 추가는 쉽지만 제거는 breaking 이다.

## 2. 명명 · 구조
- 일관된 **네이밍·케이스 컨벤션**(예: 필드 케이스, 리소스 복수형)을 정하고 지킨다.
- **리소스/도메인 중심**으로 설계한다. 동작을 리소스에 자연스럽게 매핑한다.
- 약어·모호한 이름을 피하고 의도를 드러내는 이름을 쓴다.

## 3. 요청 · 응답
- **명시적 스키마**: 입력·출력의 타입·필수 여부·형식을 명확히 한다.
- **모든 입력을 검증**한다(신뢰 경계에서, `security-guidelines.md`). 검증 실패는 명확한 에러로 돌려준다.
- 응답 형태를 일관되게 유지한다. 같은 개념을 엔드포인트마다 다르게 표현하지 않는다.

## 4. 에러 처리
- **일관된 에러 형태**를 정한다(예: 코드·메시지·상세 필드). 소비자가 프로그램적으로 분기할 수 있는 **안정적 에러 코드**를 제공한다.
- 프로토콜 시맨틱을 지킨다(예: HTTP 상태 코드를 의미에 맞게).
- 에러 메시지는 **행동 가능**해야 한다(무엇이 왜 잘못됐고 어떻게 고치는가). 내부 구현 세부는 노출하지 않는다.

## 5. 버저닝 · Deprecation
- **SemVer** 로 호환성을 신호한다(`branching-strategy.md`). breaking change 는 major 로만.
- 버전 전략(URL·헤더 등)을 정하고 일관되게 쓴다.
- **Deprecation 정책**: 곧바로 제거하지 않는다. 사전 공지 → 유예 기간 → 마이그레이션 경로 제공 → 제거. 폐기 예정을 문서·응답으로 알린다.

## 6. 하위 호환 (Backward Compatibility)
- **안전한 변경(additive)**: 선택적 필드·새 엔드포인트 추가.
- **깨는 변경(breaking)**: 필드 제거·의미 변경·필수화·타입 변경. 새 버전에서만.
- **관대하게 받고 엄격하게 보낸다**: 알 수 없는 필드는 무시하도록 설계해 확장 여지를 남긴다.

## 7. 대량 데이터
- 목록 응답에는 **페이지네이션**을 기본으로 둔다(무한정 반환 금지). 필터·정렬 규칙을 일관되게 제공한다.
- 페이지네이션 방식(offset vs cursor)의 트레이드오프를 이해하고 선택한다.

## 8. 멱등성 · 안전성
- 메서드/연산의 **안전성·멱등성 시맨틱**을 지킨다(읽기는 부수효과 없음, 재시도 가능한 연산은 멱등하게).
- 네트워크 재시도를 고려해, 중복 요청이 상태를 오염시키지 않도록 설계한다.

## 9. 문서화
- 공개 API 는 **문서화**한다(`documentation-standards.md`). 가능하면 기계가 읽는 명세(예: OpenAPI/IDL)로 두어 코드와 함께 갱신한다.
- 예시 요청·응답, 에러 사례를 제공한다.
